# Статистика прогонов

[English](../en/stats.md) · [К README](../../README.ru.md)

auto-bmad хранит в проекте статистику каждого прогона story: время, токены по ролям
и моделям, сабагенты, вызовы инструментов, проходы и находки ревью, вердикты проверок.
По ней видно, чем уровни отличаются и куда уходит бюджет прогона.

## Статистика нативных запусков Codex

`stats show`, `record` и `backfill` собирают нативные журналы вместе с прежней статистикой
CLI и Claude. Нативные строки содержат время задач, агентов, циклы ремонта и технические
повторы. Время всего запуска показано отдельно от суммы времени задач: параллельные задачи
могут пересекаться по времени.

Для счётчиков Codex привяжите точные ID главного чата и его хода из инструментов клиента:

```bash
auto-bmad stats record --repo . --session /absolute/path/to/native/session.json \
  --codex-thread <root-thread-UUID> --codex-turn <root-turn-UUID>
auto-bmad stats show --epic 1 --last 1 --calls --repo .
```

Привязка выполняется в начале запуска и для каждого нового хода продолжения. Она проверяет
репозиторий и ход в локальном журнале; один корневой ход нельзя отнести к двум запускам.
Не запускайте два отдельно учитываемых прогона в одном корневом ходе. Затем `show`/`backfill`
обновляют привязанные запуски автоматически. Старый запуск можно привязать через `record`.
Если клиент не раскрывает ID, время сохраняется, расход остаётся неизвестным; ID не угадывают.

Сборщик читает `$CODEX_HOME/sessions` (по умолчанию `~/.codex/sessions`), без приватной базы
приложения. Дочерние чаты связываются по метаданным родителя и точному ID корневого хода.
Суммируется только `token_usage_record.usage`, один раз на пару чат/ответ. Накопительные
`token_count`, итоги хода/чата и копии внутри compaction не прибавляются. Кэш входит во вход,
reasoning — в выход. Без записей расхода каждого ответа учёт недоступен; отсутствующие файлы,
незавершённые и некорректные измерения дают частичный или недоступный результат.

В JSON `tokens` содержит задачи, `tokens_with_orchestrator` — также главный чат; таблица
показывает оба итога. Неизвестное отмечается прочерком, а частичные числа — измеренной частью.
Текущий ход отчёта ещё не завершён, поэтому его покрытие может быть частичным. Роль берётся
из журнала по пути/ID агента; незарегистрированные дочерние агенты учитываются как
`unattributed`, модель `?`. Настроенные модель и effort не являются измерением провайдера.
В игнорируемую статистику попадают счётчики, ID и состав волн, без промптов и исходного кода.
Прежние данные CLI/Claude не приписываются нативному запуску. Описание старого сборщика
ниже относится к транскриптам Claude.

## Команды

```bash
auto-bmad stats show [--epic N] [--last N] [--calls] [--json] [--repo .]
auto-bmad stats record --session <id сессии> [--repo .]
auto-bmad stats backfill [--repo .]
```

| Команда | Что делает |
|---|---|
| `show` | таблица по story и итог по проекту. `--epic N` — только эпик N; `--last N` — только последние N сессий; `--json` — итог и строки в JSON |
| `record` | собирает одну сессию Claude Code и пишет её в проект. Прогон зовёт её сам после каждой story (в параллельном режиме — раз на волну) через `auto-bmad story-finish --session ${CLAUDE_SESSION_ID}`. Хук плагина `SessionEnd` зовёт её ещё раз, когда сессия закончилась |
| `backfill` | собирает прошлые сессии этого проекта, которых ещё нет в статистике, — для прогонов до появления статистики или если `record` не сработал. Записанные сессии не переписываются |

Коды выхода: 0 — сделано, 1 — ошибка вызова, 2 — нечего записать или показать.

## Что меряется

По каждой story:

- id, эпик, уровень, статус (`done` / `blocked`), коммит, число изменённых файлов;
- начало, конец, минуты. Конец — последний отчёт заходов и проверок story: агент, который
  проснулся после своего отчёта (закончилась фоновая команда), story не удлиняет.
  Минуты — время, когда заходы и проверки story работали: объединение их отрезков от старта
  до отчёта. Пересечения считаются один раз, пауза между остановленным заходом и его
  перезапуском не считается. Поэтому минуты могут быть меньше, чем конец минус начало;
- токены: всего, по моделям и по ролям (оркестратор, прогон story, реализатор, слои ревью, разбор находок,
  проверяющий…), а ещё по ролям и моделям вместе (`by_role_model`): видно, какая модель
  реально работала в роли после переопределения [`[roles.*]`](config.md#roles);
- сабагенты по типам; вызовы инструментов по именам;
- израсходованные проходы ревью, остался ли открытым повторный проход, отложенные находки;
- проходы ревью и находки по вердиктам, решениям и слоям ревью — из секции спеки
  `## Review Triage Log` (слои по именам BMad: blind, edge, intent, verification).
  Спеку параллельной story скрипт читает из основного дерева, если её worktree уже удалён;
- заходы починки после проверок и вердикт каждой проверки. Перезапуск story до её первой
  проверки — не починка.

Ещё строка на сессию — для оркестратора: время, вызовы инструментов и токены.

Пример `show`:

```bash
auto-bmad stats show --epic 1
```

В таблице колонки: story, уровень, статус, минуты, выход≈, вход, кэш, агентов, проходов,
находок. Под ней строки итога: число историй (done / blocked) и общее время, средние токены
на story, средние проходы ревью, находки и сабагенты, строка разбора находок, выход по ролям
с моделями каждой роли в скобках, самые частые инструменты.
Подписи в таблице — на английском.

Строка разбора находок (`Triage`) в сводке `show` показывает, как сессия story распорядилась
находками ревью: `patch` (починили), `defer` (отложили), `reject` (отклонили) и «в спеку»
(`intent_gap`, `bad_spec`) — доли от разобранных находок, затем доли вердиктов `low` и `false`.
Строка видна, только если в журналах спек есть разобранные находки. `low` в основном ставит
правило отсева (факт B), `false` — сессия после чтения кода. Если разбор стал хуже, ждите роста
`reject` и `false` и падения `patch`. Сравнивайте прогоны одного уровня: уровень меняет слои
ревью и их модели, а значит, и сами находки. В `--json` строка есть по уровням, в `by_level`.
См. [Под капотом](engine.md).

В отчёт по эпику прогон вставляет три строки итога из `auto-bmad stats show --last 1`.

## Откуда данные и куда пишутся

Источник — транскрипты Claude Code, а не память модели:
`~/.claude/projects/<проект>/<сессия>.jsonl` для оркестратора и
`…/<сессия>/subagents/agent-*.jsonl` для сабагентов любой глубины
(`$CLAUDE_CONFIG_DIR/projects`, если эта переменная задана). Находки ревью — из спеки,
которую назвал сабагент story.

Хранение — `.auto-bmad/stats/runs.jsonl` в проекте (в его основном дереве, и для
[прогона в своём worktree](running.md#прогон-в-своём-worktree)): строка на прогон story плюс строка
на сессию для оркестратора. Папка закрыта от git локально через `.git/info/exclude`.
Повторная запись той же сессии заменяет её строки, а не дублирует.

**Страховка.** У плагина есть хук `SessionEnd`. Сессия, в которой работал
`bmad-story-runner`, закончилась — хук пишет её через `stats record`. Хук запускает
Claude Code, а не модель, поэтому права на него не действуют. Отклонённый вызов в прогоне
ничего не теряет. Хук запускает запись в фоне и сразу выходит: хуку плагина `SessionEnd`
Claude Code даёт только 1,5 секунды. Другие сессии хук пропускает.

Хранятся только счётчики: id, уровень, статус, время, числа, токены, имена инструментов
и типов агентов. Ни текста промптов, ни кода, ни путей, ни текстов находок.

## Оговорка: выходные токены — оценка

- **Вход и кэш — точные**, из транскрипта.
- **Выход — оценка** (помечен `≈`): по объёму видимого текста ответов и входов инструментов,
  около 3,5 символа на токен. Транскрипт пишет `output_tokens` на старте ответа, и это
  число занижено в разы.
- Рассуждения модели в оценку не входят.
- Цены не считаются.

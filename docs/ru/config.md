# Конфиг

[English](../en/config.md) · [К README](../../README.ru.md)

Конфиг необязателен: без него прогон работает на встроенных умолчаниях. Конфиг задаёт:

| Раздел | Что задаёт |
|---|---|
| [`[run]`](#run) | уровень по умолчанию, параллельные волны и ширину волны, разбор находок ревью в сабагенте |
| [`[roles.*]`](#roles) | совместимые прежние настройки Claude для каждого субагента по его назначению |
| [`[executors.codex]`](#компактные-модели-codex) | модели и effort каждого субагента, общие умолчания и явные отличия уровней |
| [`[repair_limits]`](#repair_limits) | отдельные бюджеты спеки, ревью и тестов на story |
| [`[verify_limits]`](#verify_limits) | устаревшая настройка; заменена на repair_limits |
| [`[[verify]]`](#verify) | проверки после story: тесты проекта, эмулятор Android, браузер, свои команды |
| [`[[hook]]`](#hook) | ваши скрипты на события прогона: сообщение в чат, карточка на доске |

Файл проекта `.auto-bmad.toml` пишет `/auto-bmad:setup` по тому, что нашёл в проекте.
Можно написать его и руками: возьмите за образец один из [примеров](#пример-android-проект) ниже.
После правки проверьте результат командой `auto-bmad ext config --repo .`, а модель и effort
ролей — командой `auto-bmad roles --repo .`.


## Компактные модели Codex

В Codex встроены [настройки каждого субагента](levels.md#модели): Sol/medium для story-runner, intent-alignment и verifier; Sol/high для implementer, verification-gap и triager; Luna/high для context-compiler; Astra/high для blind-hunter и edge-case-hunter. Явные общие model/effort переопределяют эти дефолты для своей группы; настройки конкретных ролей имеют больший приоритет.
Субагенты наследуют разрешения чата. Запрет правок у ревьюера не создаёт отдельную песочницу.
Claude сохраняет свои модели ролей; общие инструкции находятся в `prompts/roles/`.
Можно использовать их или записать только отличия:

```toml
[executors.codex]
model = "gpt-6.1-sol"
effort = "high"
review_model = "gpt-6-astra"
review_effort = "high"

[executors.codex.levels.fast]
effort = "medium"

[executors.codex.levels.deep]
review_effort = "xhigh"
```

Общий блок действует для fast, normal и deep. Уровень без своего блока наследует общий.
Effort работы и ревью задаются независимо. Общие значения — умолчания, а не имена агентов.
У каждого реального субагента своя таблица. Например, два слоя ревью могут иметь разные
effort без изменения остальных слоёв:

```toml
[executors.codex.roles.blind-hunter]
model = "gpt-6-astra"
effort = "high"

[executors.codex.roles.edge-case-hunter]
model = "gpt-6-astra"
effort = "xhigh"

[executors.codex.levels.deep.roles.edge-case-hunter]
effort = "max"
```

Для Claude используйте те же ID в `[executors.claude.roles.<id>]` с его именами моделей.
Уровень задаёт включённые проверки и глубину; он не заменяет ID слоя названием класса модели.
Порядок: встроенные → общие → уровень → общая роль → роль уровня.
Сначала local-файл перекрывает проектные значения. Неизвестные уровни, роли и ключи отклоняются даже у неактивных уровней.

Setup по умолчанию сохраняет модели клиента в приватном `.auto-bmad.local.toml`.
`setup agent --agent codex --role edge-case-hunter --model gpt-6-astra --effort high`
показывает изменение одного субагента; `--write` сохраняет его. Добавьте `--level deep`
для явного переопределения на этом уровне. Команда
`setup agent --agent codex --level fast --effort medium` меняет общие рабочие умолчания уровня.
Явный `--layer project` позволяет сохранить общие настройки. Для Claude служит `[executors.claude]`
с переопределениями общих значений, уровней и ролей. Прежние `[roles.*]` остаются запасным источником.
Оба пространства настроек могут сосуществовать; настройка одного клиента сохраняет другой.

`setup agent --agent codex --compact` переносит совместимые расширенные маршруты с точной резервной копией.
Модели и effort каждой роли и уровня сохраняются. Неподдержанные адаптеры и неполные маршруты отклоняются.
Поля executable, окружения и CLI-таймаута в нативном режиме не действуют; прежние флаги их настройки запрещены.
Не переводите названия моделей другого клиента по догадке.
Скилл выбирает текущий клиент, сохраняя default проекта. Codex использует `native` и субагентов чата.
Прежнее `backend="cli"` читается с предупреждением о переносе. AI Workspace служит установщиком, но не нужен во время запуска.

## Четыре слоя

auto-bmad читает четыре TOML-файла. Каждый следующий слой главнее предыдущего.

| Слой | Файл | Для чего |
|---|---|---|
| умолчания | `defaults.toml` в плагине | встроенные проверки и лимиты; не правьте |
| личный | `~/.config/auto-bmad/config.toml` или файл из `$AUTO_BMAD_CONFIG` | ваши хуки и предпочтения на этой машине |
| проектный | `.auto-bmad.toml` в корне репозитория | настройки проекта, общие для всех машин; его коммитят |
| локальный | `.auto-bmad.local.toml` в корне репозитория | только эта машина, поверх проектного: другая команда тестов, другая модель, проверка выключена здесь; держите его вне git |

Правила слияния:

- Таблицы (`[run]`, `[roles.*]`, `[verify_limits]`) сливаются по ключам.
- Массивы таблиц `[[verify]]` и `[[hook]]` сливаются по полю `name`. Блок с тем же `name`
  дополняет и переопределяет поля. Новый `name` добавляет новый блок.
- `enabled = false` выключает хук или проверку.
- Остальные значения (и простые массивы вроде `apis`) заменяются целиком.
- Слой, который не читается, пропускается с предупреждением. Прогон идёт дальше.

Локальный слой видят все команды, которые читают конфиг (`plan`, `profile`, `preflight`,
`roles`, `verify`, `land`, `ext`). `auto-bmad setup local --write` закрывает его от git
(дописывает в `.gitignore`). Preflight предупреждает, если он закоммичен.
[Прогон в своём worktree](running.md#прогон-в-своём-worktree) копирует его в worktree.

Собранный конфиг и список прочитанных файлов:

```bash
auto-bmad ext config --repo .
```

Выключить личный хук в одном проекте — в `.auto-bmad.toml` этого проекта:

```toml
[[hook]]
name = "notify"
enabled = false
```

`@plugin` в `command`, `detect` и `instructions` заменяется на каталог, куда поставлен
плагин. Пишите его вместо пути в кэше: путь меняется при каждом обновлении.

## `[run]`

Умолчания запуска. Флаги команды (`--fast`, `--deep`, `--no-parallel`, `--width N` и др.) главнее.

| Ключ | Значения | По умолчанию |
|---|---|---|
| `level` | `fast`, `normal`, `deep` | `normal` |
| `parallel` | `conservative`, `aggressive`, `off` | `conservative` |
| `width` | размер волны, целое ≥ 1 | `3` |
| `worktree` | `true`, `false` — прогон идёт в своём worktree на ветке `bmad/<цель>`, слить потом через `auto-bmad land` ([Запуск](running.md#прогон-в-своём-worktree)); `--worktree` / `--no-worktree` главнее | `false` |
| `triage_subagent` | `true`, `false` — разбор находок ревью в сабагенте `bmad-triager` (факт I, [Под капотом](engine.md#факты)) | `false` |

Эти настройки общие для инструмента: нативные Codex и Claude Code читают один `[run]`.
`conservative` разделяет story при зависимости, общем файле/модуле, общей точке сборки
или неясной области изменений. `aggressive` допускает пересечения файлов, но сохраняет
разделение по явным зависимостям и общим точкам сборки. `off` запускает story по очереди.
Ширина — верхний предел, а не требование заполнить каждую группу.

Неверное значение игнорируется, берётся встроенное умолчание.

## `[project_tests]`: части проекта и проверки

Выбор scopes/fallback ниже относится к старым журналам и прямым вызовам компонентных тестов.
Новые нативные сессии используют integration-full-v1: адресные development-проверки и сборка
во время разработки, полный project-tests на объединённом кандидате до изменения main.
Scopes/fallback не заменяют регистрацию адресных команд и не запускают полный fallback
в ходе разработки по новой политике.

Одна настройка для нативные Codex и Claude. Без неё сохраняется прежняя единая
проверка `project-tests`. Setup читает структуру конкретного проекта, предлагает команды
и границы частей, согласует их с пользователем и только затем сохраняет настройки.
Имена частей произвольные: веб, API, Android, iOS, общий модуль, desktop и другие.

```toml
[project_tests]
baseline = true
ignore = ["docs/**", "README.md"]

[project_tests.scopes.frontend]
paths = ["frontend/**", "contracts/**"]
command = "scripts/check.sh frontend"
timeout = 900

[project_tests.scopes.backend]
paths = ["backend/**", "contracts/**"]
command = "scripts/check.sh backend"
timeout = 1800

[project_tests.fallback]
command = "scripts/check.sh"
timeout = 1800
```

Команды в примере относятся к проекту с таким `check.sh`; setup проверяет наличие
реальных команд, а не переносит пример во все проекты. Каждая команда должна готовить
свои зависимости в свежем worktree. Команды не запускаются во время setup.

Правила выбора: изменения только `frontend/` запускают frontend; только `backend/` —
backend; обеих частей или общего `contracts/` — обе проверки. Неизвестный путь или
общая конфигурация запускает `fallback` один раз. Без `fallback` запускаются все
настроенные части. `ignore` исключает согласованные пути из выбора и ключа кэша;
служебные `.auto-bmad/` и `_bmad-output/` исключаются автоматически.

Для консервативных границ доступны дополнительные поля `[project_tests]`:
`full_paths = ["contracts/**", "frontend/package*.json", "_bmad-output/**/DESIGN.md"]`
требует `fallback` даже для пути внутри scope или `ignore`; `full_on_multiple = true`
требует fallback при изменении нескольких частей. Без fallback выполняются все scopes.
`full_patterns` — регулярные выражения Python для добавленных и удалённых строк diff
и содержимого новых файлов. Например, `full_patterns = ['fetch\s*\(', '/api/']` расширяет
проверку при изменении вызова API внутри обычного UI-файла. Файлы с таким содержимым
и `full_paths` входят также в общие входы кэша; изменения инвалидируют зависимые результаты.
Это консервативная проверка, а не полный анализ контрактов. Контроллер оценивает взаимодействия
и неясное влияние изменений, затем при необходимости запускает более широкие настроенные проверки.
Исходный baseline story сохраняется во всех исправлениях и итоговых проверках.

`setup tests` читает проект без запуска тестов. `setup tests --plan <json> --write` сохраняет согласованную
стратегию с резервной копией. Без `--write` команда показывает план; `--layer local` выбирает локальный файл.
Команды используют разрешения вызывающего клиента:

```bash
auto-bmad test --repo /path/to/worktree --base <original-commit> --name project-tests
auto-bmad test --repo /path/to/worktree --base <original-commit> --name project-tests/frontend
```

План компонентов может продолжаться в фоне. `--wait` ограничивает ожидание вызова; повтор присоединяется
к тому же прогону. `--rerun` обновляет устаревшие результаты и baseline. Недавний результат может
использоваться повторно по правилам кэша test helper. Кэш не подтверждает текущее здоровье внешних сервисов.

### Адресные проверки и итоговая проверка

Отдельная проверка разработки принимает файлы или узлы тестов и не меняет итоговую проверку:

```toml
[project_tests.development.backend]
command = "scripts/check.sh backend"
targets = ["backend/tests/test_*.py"]
timeout = 1800
```

```bash
auto-bmad test --repo /path/to/worktree --name dev/backend --target backend/tests/test_example.py::test_case
```

Команда принимает селекторы относительно корня проекта как позиционные аргументы.
Нужен хотя бы один селектор существующего разрешённого файла. Опции shell и произвольные команды вместо селектора запрещены.
Сначала исправьте весь известный список упавших тестов, затем повторите эти проверки
и затронутые регрессии; другая зелёная проверка не закрывает исходный сбой. Повторное
независимое ревью нужно после обширных/рискованных изменений. Для точечных исправлений
свежий специалист подтверждает применимость исходного ревью. Новая команда
`native check --request PLAN.json` сохраняет адресные тесты и сборку для complete.
`land --native-session SESSION --story ID ...` проверяет полный набор на объединённом
кандидате до изменения main; finalize использует действующие доказательства того же дерева,
конфига, команд и логов. Старые журналы сохраняют прежний порядок итоговых проверок.

Зарегистрируйте реальную команду компиляции/сборки вместе с development:

```toml
[project_tests.build.compile]
command = "scripts/compile.sh"
timeout = 900
```

`setup tests` показывает зарегистрированные команды и пробелы; `--plan FILE --write`
сохраняет согласованные development/build с резервной копией. Без адресной команды helper
сообщает пробел, а не запускает полный набор. Если у проекта нет этапа сборки, запрос
разработки должен содержать явную причину `build_not_applicable`. Setup и разработка по новой
политике не запускают полный baseline. Досрочный full требует конкретной причины широкого
риска; после упавшего full сначала должны пройти настоящие адресные тесты и сборка.

## `[roles.*]`

Прежний формат настроек Claude для каждого субагента. Для новых настроек используйте
`[executors.claude.roles.<id>]` и `[executors.codex.roles.<id>]`.
Пустой конфиг сохраняет умолчания клиента из [таблицы моделей](levels.md#модели).

```toml
[roles.implementer]
model = "sonnet"
effort = "high"

[roles.edge-case-hunter]
effort = "high"

[roles.story-runner]
model = "opus[1m]"   # Opus с контекстом 1M; просто "opus" — обычный контекст
effort = "high"
```

| Ключ | Значения |
|---|---|
| `model` | `sonnet`, `opus`, `opus[1m]`, `haiku`, `fable`, `default` |
| `effort` | `low`, `medium`, `high`, `xhigh`, `max`, `default` |
| `provider` | только `anthropic`; другой провайдер пока не поддерживается |

Субагенты: `story-runner`, `implementer`, `context-compiler`, `blind-hunter`,
`edge-case-hunter`, `intent-alignment`, `verification-gap`, `triager`, `verifier`.
У каждого слоя ревью собственные модель и effort. Оркестратор — главный чат:
его модель вы выбираете в клиенте, вне этого конфига. Неизвестный ID слоя требует
явной поддержки адаптера; подменять его другим ревьюером нельзя.

Как это работает. Значение доходит до сабагента параметрами `model` и `effort` вызова `Agent`.
Они главнее модели и effort агент-типа. Для story-runner и verifier параметры передаёт скилл,
для остальных ролей — движок по профилю уровня (факты E, G и I). Файл агента в `.claude/agents/`
для этого не подходит: Claude Code читает агент-типы один раз, при старте сессии.

Ограничения:

- **Opus с контекстом 1M — пишите `model = "opus[1m]"`.** Просто `opus` даёт обычный
  контекст, preflight об этом предупреждает. `opus[1m]` доступен только ролям, у которых
  он стоит в агент-типе: story-runner и implementer. Вызов `Agent` не умеет передать `[1m]`,
  поэтому `opus[1m]` оставляет модель агент-типа, а у другой роли это ошибка preflight.
- Остальные значения `model` — псевдонимы из списка.
- `default` (или само значение по умолчанию, например `opus[1m]`) снимает переопределение
  нижнего слоя. Так проект возвращает роли модель агент-типа, если личный конфиг её сменил.
- Неверное значение, неизвестный `provider` — preflight останавливает прогон.
  Неизвестная роль или ключ — предупреждение, ключ не применяется.
- Какая модель реально работала в роли, видно в `auto-bmad stats show`, в строке
  «Output by role».

Проверить, что получилось после слияния слоёв: `auto-bmad roles --repo .`.

## Перенос прежних имён ролей

Прежние ключи классов моделей читаются для совместимости; setup записывает ID субагентов
по их назначению. Перенос сохраняет итоговые модель и effort каждой роли на каждом
уровне, включая явные переопределения:

| Прежний ключ | Какие субагенты наследуют его значения |
|---|---|
| `reviewer-lite` | `intent-alignment` на fast/normal |
| `reviewer-mid` | `blind-hunter`, `edge-case-hunter`, `verification-gap` на fast/normal |
| `reviewer` | все четыре слоя ревью на deep |
| `compiler-lite` | `context-compiler` |

Неактивные слои остаются выключенными согласно уровню. Явная настройка субагента имеет
приоритет над старым псевдонимом. Старые имена не используются для запуска: каждый слой
всегда запускается под собственным ID. Перед переносом проверьте итоговые значения
ролей и точную резервную копию setup. Разные прежние настройки нельзя заменять одной
общей моделью ревью с потерей значений.
Setup переносит только выбранный файл. Если преобразование перебивает старые настройки
более высокого слоя, setup отказывает в записи: сначала перенесите высокий слой
(обычно `--layer local`), затем повторите перенос нижнего. Остальные файлы не меняются.

## `[repair_limits]`

Независимые бюджеты на одну story во всех режимах (`fast`, `normal`, `deep`):

```toml
[repair_limits]
spec = 2
review = 5
tests = 10
no_progress = 3
```

`spec` расходуется только на исправление плана/спеки (`bad_spec`); `review` — на
правки по ревью и находки agent-проверок; `tests` — на исправление упавших командных
проверок. Тестовые попытки не расходуют другие бюджеты. Один цикл — пакет правок,
а не одна находка. Счётчики сохраняются между повторными проходами внутри запуска
story, включая замену агентов. Resume нативного журнала сохраняет счётчики и baseline;
он не выдаёт новый бюджет молча. Адаптер Claude сохраняет прежний учёт по story/baseline.
Автоматического возобновления нет.

`no_progress` — сколько тестовых попыток подряд допустимо без прогресса. Прогресс —
успешный повтор той же проверки или строгое сокращение множества известных упавших
тестов (строки `FAILED <id>` или `FAIL:/ERROR: <id>`). Изменённый текст ошибки,
изменённый код и неизвестный формат вывода сами по себе не доказывают улучшение.
При неизвестном формате счётчик сбрасывается успешной проверкой или подтверждённым
хостом точным совпадением с исходной scoped-проверкой; произвольный пропуск не подходит.
Нативный журнал использует результаты `check` и события `repair`.
Сохранённый адаптер Claude использует `verify attempt`/`verify observe`.
Повтор без правки не расходует новую попытку; после начатой попытки тот же красный
результат, включая кэшированный, считается отсутствием прогресса.

Все известные тестовые сбои исправляются одним пакетом до повторного запуска тестов.
Повторное независимое ревью нужно только после обширных/рискованных изменений с момента
предыдущего ревью. Точечные исправления проверяет главный чат, сохраняя обоснование
применимости исходных отчётов. Первое независимое ревью и итоговые настроенные проверки обязательны. Нельзя отключать тесты или ослаблять
ожидания ради зелёного результата. Ошибки доступа/окружения не являются починкой кода;
распознанный сбой окружения при повторе возвращает списанную тестовую попытку.
Исчерпание бюджета или отсутствие прогресса сохраняет работу и даёт `blocked`.

Значения — целые числа от нуля; `0` запрещает соответствующую категорию исправлений,
а не снимает лимит. `no_progress` — положительное целое. Неизвестные ключи отклоняются.
Таблица сливается по ключам во всех четырёх слоях; изменения требуют нового подготовленного
запуска. Прежние `repair_limits.fast/normal/deep` нужно заменить категориями выше.

## `[verify_limits]` (устарело)

Больше не ограничивает исправления; при наличии выдаётся предупреждение.
Перенесите нужный бюджет в `repair_limits.tests` или `repair_limits.review`.
Выбор проверок по уровню задаётся `[[verify]].levels`.

## `[[verify]]`

Проверка после story. Все поля и примеры — [Проверки](checks.md#поля-блока-verify).

| Поле | Коротко |
|---|---|
| `name` | имя, ключ слияния |
| `kind` | `command` или `agent` (по умолчанию `agent`) |
| `levels` | по умолчанию `["normal", "deep"]` |
| `command` | команда для `kind = "command"`; `@test_command` — найденная команда тестов |
| `detect` | команда: подходит ли проверка к диффу story |
| `requires`, `install_hint` | нужный проверке скилл и как его поставить |
| `preflight` | команда, которую preflight запускает перед прогоном; поля проверки получает JSON в stdin; код 1 — предупреждение, 2 — блок |
| `instructions` | markdown для агента |
| `on_fail` | `fix` (по умолчанию) или `note` |
| `timeout` | секунды для `kind = "command"`, по умолчанию 1800 |
| `enabled` | `false` выключает |
| другие поля | уходят агенту как поля проекта |

## `[[hook]]`

Команда на события прогона. Подробно — [Хуки](hooks.md).

| Поле | Что это |
|---|---|
| `name` | имя, ключ слияния |
| `events` | список событий, например `["story-done", "story-blocked", "run-end"]` |
| `command` | команда оболочки, идёт через `sh -c` из корня проекта |
| `timeout` | секунды, по умолчанию 120 |
| `enabled` | `false` выключает |

## Пример: Android-проект

`.auto-bmad.toml`:

```toml
# Умолчания запуска: флаги команды главнее.
[run]
level = "normal"            # fast | normal | deep
parallel = "conservative"   # conservative | aggressive | off
width = 3                   # историй в волне

# Увеличенный отдельный бюджет тестовых исправлений.
[repair_limits]
tests = 15

# Юнит-тесты вместо найденного "./gradlew test".
[[verify]]
name = "project-tests"
command = "./gradlew :app:testDebugUnitTest"
timeout = 2400

# Проверка фичи на эмуляторе через adbm (только для story с UI).
[[verify]]
name = "adbm"
build = "./gradlew :app:assembleDebug"
apk = "app/build/outputs/apk/debug/app-debug.apk"
package = "com.example.app"
apis = [35]
notes = "Приложение ставит FLAG_SECURE: перед кадрами выключи защиту скриншотов в его настройках."
# serial = "<serial устройства>"   # разрешить физическое устройство; без него — только эмуляторы
# bug_before_after = false         # без сборок «до и после» для багов

# Веб: проверка в браузере через mockmatch (только для story с веб-UI) и сверка с дизайном.
[[verify]]
name = "mockmatch"
serve = "npm run dev"
url = "http://localhost:5173"
design_project = "https://claude.ai/design/p/<id>?file=Home.dc.html"   # свежая копия на каждую проверку
# design_artifact = "https://claude.ai/artifact/<id>"   # артефакт claude.ai типа «Design»; нужен design
design = "design/home.html"   # запасной вариант без входа в Claude Design; подойдёт и HTML-макет или PNG
widths = [1440, 390]

# Статический анализ: проблемы в отчёт, без починки.
[[verify]]
name = "lint"
kind = "command"
command = "./gradlew :app:lintDebug"
on_fail = "note"
timeout = 1200

# Хук проекта: строка после каждой story.
[[hook]]
name = "notify"
events = ["story-done", "story-blocked", "run-end"]
command = "python3 tools/auto-bmad-notify.py"
timeout = 60
```

## Пример: Python-проект

`.auto-bmad.toml`:

```toml
[run]
level = "normal"
parallel = "off"            # по одной story

# Тесты через uv вместо найденного "pytest".
[[verify]]
name = "project-tests"
command = "uv run pytest -q"
timeout = 900

# Проверка типов; проблемы чинит движок, до лимита уровня.
[[verify]]
name = "types"
kind = "command"
command = "uv run mypy src"
on_fail = "fix"
timeout = 600
```

Блок `adbm` здесь не нужен: проверка идёт только в проектах с `settings.gradle(.kts)`.
Блок `mockmatch` тоже не нужен: проверка идёт только для story, которые трогают веб-UI.

## Локальное слияние эпика

```toml
[execution]
backend = "native"
merge_policy = "auto-main" # по умолчанию "manual"
```

В Codex главный чат завершает все stories и tracking, затем сливает проверенный эпик в локальный `main`.
Ветка main должна быть открыта в локальном worktree. Если main изменился, оркестратор объединяет изменения
в рабочей ветке и повторяет затронутые проверки. Конфликты, незавершённые проверки и чужие правки
сохраняют работу и дают конкретный блокер. Редакционные вопросы сами по себе не мешают слиянию.
Отдельная story не сливается автоматически. Push и деплой выполняются отдельно.
Нативный журнал хранит проверки и завершение; чат сообщает фактический результат слияния.

## Совместимость ограниченных заданий

Новые нативные журналы сохраняют `checkpoint_policy="bounded-checkpoints-v1"`.
Это версия протокола сессии, не настройка модели. Без поля действует прежний контракт.
На пачку допускается до 3 локальных попыток исправления и до 3 диагностических
проверок; прежние story/no-progress лимиты могут остановить работу раньше.
Смена агента и resume не сбрасывают счётчики. У development/build-команд есть
необязательное `independent = false`. Модели и настройки Claude сохранены;
работающие журналы и закреплённые пакеты не мигрируют.

For bounded-checkpoints-v1, older `land --native-session` examples additionally
require `--native-task TASK`: stage the full gate, complete/accept that task receipt,
then dispatch a fresh integration task to land using the accepted exact-candidate gate.
The single-call examples remain valid only for the legacy session policy.

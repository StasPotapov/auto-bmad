# Под капотом: движок BMad и профиль уровня

[English](../en/engine.md) · [К README](../../README.ru.md)

auto-bmad сам не пишет и не ревьюит код. Всю работу над story делает движок BMad
`bmad-build-auto`: спеку, код, слои ревью, разбор находок, починку и коммит. auto-bmad
запускает движок по одной story и меняет его поведение через настройки. Файлы движка
он не правит.

## Кто что делает

| Движок BMad (`bmad-build-auto`) | auto-bmad |
|---|---|
| планирует спеку `spec-<story>.md` | строит очередь story из `sprint-status.yaml` и `epics.md` |
| собирает `epic-<N>-context.md` | выбирает уровень и пишет профиль уровня |
| пишет код в сабагенте implementer | запускает каждую story в своём сабагенте, `bmad-story-runner` |
| ревьюит дифф параллельными слоями, разбирает находки, чинит | ведёт параллельные волны в git worktree и сливает их |
| выполняет команды из раздела `## Verification` спеки | проверяет story после движка: тесты проекта, устройство, браузер |
| коммитит story | двигает `sprint-status.yaml`, пишет открытые вопросы, зовёт хуки, пишет статистику |

## Как auto-bmad меняет движок

Движок собирает настройки из слоёв. Более поздний слой главнее:

1. `customize.toml` внутри скилла движка — значения BMad по умолчанию;
2. `_bmad/custom/bmad-build-auto.toml` — настройки вашего проекта;
3. `_bmad/custom/bmad-build-auto.user.toml` — верхний слой, BMad оставил его для локальных правок.

auto-bmad пишет третий файл — **профиль уровня** — один раз на прогон (`auto-bmad profile`).
В профиле две вещи:

- **факты** (`persistent_facts`) — правила простыми словами. Движок загружает их в начале
  и следует им весь прогон. Факты дописываются к фактам вашего проекта;
- **выключенные слои ревью** — запись с `id` слоя и пустой инструкцией.

Файлы движка остаются нетронутыми, поэтому обновление BMad правки не теряет. Файл профиля
закрыт от git локально (`.git/info/exclude`), а следующий прогон его перепишет: руками
его не правьте. Если этот файл написали вы сами (в нём нет метки auto-bmad), прогон
не станет его перезаписывать и остановится.

## Зачем движку правки

Движок рассчитан на работу рядом с человеком. Без человека и на длинном эпике у него три
слабых места:

- **Лишняя работа и расход.** Второй круг ревью из-за двух находок `medium`, выдуманные
  находки ради минимума, полная проверка по коду каждой мелочи, до пяти циклов починки спеки.
- **Одна модель везде.** Движок требует, чтобы слои ревью работали на модели сессии. Тогда
  код пишет и ревьюит одна и та же модель, и она пропускает свои же слепые пятна.
- **Поломки в Claude Code.** Движок запрещает заканчивать ход, пока ждёт сабагентов. А сабагенты
  в Claude Code асинхронные: без правки прогон крутится на пустых вызовах.

## Факты

| Факт | Движок без него | С фактом | Уровни |
|---|---|---|---|
| **A** — второй круг ревью | второй круг запускается, если починили находку `high` **или две находки `medium`** (step-04) | только если починили находку `high` | все |
| **B** — отсев при разборе | каждую находку проверяют по коду | находку, которая не называет последствий для пользователя или разработчика, ставят в `low` без чтения кода. Потерю данных, неверный результат, безопасность, падение и сломанную сборку проверяют всегда | все |
| **C** — лимит циклов починки | до 5 циклов `bad_spec`: код откатывают, спеку правят, story делают заново | 1 / 2 / 3 по уровню, дальше `blocked` | все |
| **D** — минимум у Blind Hunter | слой обязан найти не меньше N проблем, N растёт с размером диффа | «сообщи всё, что нашёл; пустой список — тоже ответ» | `normal`, `deep` |
| **E** — модели | слои ревью работают на модели сессии | implementer и каждый слой работают на типах агентов плагина: код ревьюит другая модель | все |
| **F** — асинхронные сабагенты | «не заканчивай ход, пока ждёшь уведомления» | закончи ход строкой о том, чего ждёшь; пустые вызовы запрещены | все |
| **G** — контекст эпика | его собирает модель сессии | его собирает `bmad-compiler-lite` (Haiku): это закрытая выжимка из документов планирования | `fast`, `normal` |
| **H** — экономия контекста | сессия читает весь файл диффа и перечитывает спеку, контекст эпика и `workflow.md` | дифф меньше 30 000 символов читается целиком; больший — по форме, нужным кускам и новым файлам, а ревьюеры читают его целиком сами; повторных чтений нет; у находки с маршрутом `reject` или вердиктом `false` / `low` записано, какой код прочитали, кроме отсеянных фактом B; код для всех находок прохода собирает один вызов `auto-bmad evidence`, а не `grep` на каждую находку | все |
| **I** — разбор в сабагенте | сессия разбирает находки в своём большом контексте | вердикты и маршруты (Classify из step-04, шаги 1–3) даёт сабагент `bmad-triager` с чистым контекстом. Он ничего не меняет: починка, журнал разбора и возвраты к спеке остаются в сессии. По умолчанию выключен: `[run] triage_subagent = true` | все, если включён |

Факты A–D опираются на замер по 15 готовым story. Обоснование каждого записано в тексте
самого факта. Факт H новый, на прогонах его ещё не мерили. Его риск — разбор находок:
сессия видит меньше изменения сразу и может отклонить настоящую находку. Следите за строкой
`Triage` в `auto-bmad stats show` (см. [Статистика](stats.md)).

Факт I — эксперимент. Он должен снизить чтение у story-runner, но меняет схему движка.
Поэтому он выключен, пока парный прогон одного эпика с ним и без него не покажет эффект.
Выключенный флаг даёт тот же профиль, что и без ключа. С включённым флагом в
`auto-bmad stats show` появляется отдельная роль `triager`.

Выключенные слои ревью: на `fast` — Blind Hunter и Verification Gap, на `normal` —
Verification Gap. Модели каждого слоя по уровням — в [Уровнях](levels.md#модели).

## Где точный текст

Факты генерирует `scripts/write_profile.py` плагина. Посмотреть профиль уровня в проекте:

```bash
auto-bmad profile --level normal --repo .
cat _bmad/custom/bmad-build-auto.user.toml
```
